# Decisions log

Autonomous decisions made while implementing iOS copy/paste (2026-07-04), for review. Not checked into version control conventions elsewhere in this repo — delete or fold into commit messages once reviewed.

## Context

Goal: working copy/paste on iPad WebVM (currently impossible — no external keyboard, xterm.js blocks native iOS text selection via `user-select:none` and only implements mouse-driven selection).

## Decisions so far

- **2026-07-04 — Chose `@wterm/dom` + `@wterm/ghostty` over patching xterm.js in place.** User's explicit call after both options were designed and adversarially verified. Tradeoff accepted: younger/less-proven dependency, in exchange for native DOM-based selection/copy/paste instead of synthetic touch-event hacks. VT-compliance for vim/htop is the main open risk, being investigated before implementation.

- **2026-07-04 — REVERSED: dropped the wterm swap, implementing the xterm.js-patch design instead.** The requested investigation into `@wterm/ghostty`'s VT compliance came back with hard evidence, not a hedge: six-plus confirmed, currently-open, reproduced GitHub issues hit exactly vim/htop/tmux (invisible cursor over `vim`'s `cursorline`/`htop` row-highlight — #88; alt-screen color leak after quitting any TUI — #86; ACS box-drawing broken, so tmux/htop panel borders render as literal `qqqqq` — #49; dense-SGR renderer corruption surviving even a resize, matching colored `gcc`/`objdump` output — #78; wide-char cursor desync that corrupts the whole grid for the session — #52/#71/#54). The wterm maintainers themselves have never published a demo running vim/htop/tmux against the ghostty core — the one real-shell demo uses the lightweight built-in core, not ghostty, by default.
  Worse, and directly disqualifying given *why* this swap was chosen: **two open, unresolved issues (#32, #41) report `@wterm/dom`'s input handling is currently broken on iOS Safari** — the hidden textarea is positioned off-viewport with `pointerEvents: none`, which plausibly blocks the soft keyboard from opening at all AND blocks the native paste path this swap exists to deliver.
  This is new evidence that wasn't available when the swap was chosen, and it's decisive enough (both VT-compliance, the project's core purpose, and the specific iOS-paste mechanism the swap was for) that continuing anyway would be a bad call. Reverting to the already-designed, already adversarially-verified xterm.js-patch approach (long-press touch→synthetic-mouse selection bridge with capture-phase listeners, `navigator.clipboard.writeText()` for copy, a native `UIPasteboard`→`WKScriptMessageHandler` bridge for paste, plus an OSC 52 handler) — it doesn't touch xterm.js's rendering/VT-parsing at all, so it carries none of this risk. Flagging this reversal explicitly rather than silently swapping approaches.

- **2026-07-04 — Implemented the xterm.js-patch design in `src/lib/WebVM.svelte`, `ios/App/WasmWebView.swift`, `src/lib/global.css`.** Build verified clean (`WEBVM_MODE=ios npm run build`), boot verified clean via the local Playwright rig (shell reaches `root@:~#`, zero console errors — including confirming the fix for a real bug caught by the build itself: the paste bridge's `window.__webvmPaste` assignment had to be moved inside `initTerminal()` rather than top-level script scope, since this file's `<script>` body also runs during SvelteKit's SSR prerender, where `window` doesn't exist — a top-level assignment would have crashed the build).

- **2026-07-04 — Checked `coder/ghostty-web` (a separate project from `vercel-labs/wterm`, per the user's question) and did not switch to it.** Read its actual source (`lib/renderer.ts`, `lib/selection-manager.ts`, `lib/input-handler.ts`): confirmed **canvas-rendered** (`CanvasRenderer`, `canvas.getContext('2d')`) with its own custom, non-native `selection-manager.ts` — grepped for touch/pointer selection handling, found none. Same fundamental architecture as xterm.js for this problem (no native DOM text for iOS to select), so it would not obviate the custom touch-bridging code just implemented — it would only trade a mature, battle-tested VT parser for an unverified one, for no net gain on the actual copy/paste goal. It does have a `link-detector.ts` (a `WebLinksAddon` equivalent), a nice-to-have not present in wterm, but not worth another full swap + VT-compliance re-investigation given a working, tested solution is already in place.

- **2026-07-04 — Found and fixed a real bug during testing: synthetic `MouseEvent`s need `detail: 1`.** xterm.js's `SelectionService.handleMouseDown` branches on `e.detail` (1/2/3 = single/double/triple click) to decide `_handleSingleClick` vs. double/triple; a JS-constructed `new MouseEvent(...)` defaults `detail` to `0`, matching none of those branches, so `selectionStart` was silently never set and no amount of subsequent synthetic `mousemove`/`mouseup` produced a selection. Root-caused via the compiled `lib/xterm.js` source (not guesswork) after touch-drag testing showed the long-press/arm/dispatch sequence firing correctly but `term.hasSelection()` staying false. One-line fix: added `detail: 1` to the synthetic `MouseEvent` options in `dispatchMouse()`.

- **2026-07-04 — Full end-to-end verification, all via the real pipeline (not mocked):** touch-drag selection (via synthetic `TouchEvent`s dispatched under an emulated-touch-capable Playwright context, confirmed the actual xterm.js `SelectionService` registers a real selection), Copy (tapping `.xterm-copy-btn` puts the exact dragged text on the real system clipboard), Paste (seeding the clipboard + tapping `.xterm-paste-btn` — Chromium fallback path — resulted in the **guest shell actually executing** `echo PASTE_TEST_...` and echoing it back), OSC 52 (a real guest `printf '\e]52;c;...'` command correctly wrote to the real clipboard). `vim examples/c/helloworld.c` opens/quits cleanly (alt-screen, status line, cursor) — zero VT-compliance regression, as expected since xterm.js's rendering/parsing was never touched. Full iOS build (`ios/build.sh`) compiles cleanly (confirms the new Swift `nativePaste` bridge has no type errors) and boots to the shell prompt on the simulator, with the paste button correctly visible (confirms `isTouchDevice` detection works on the real target). **Not verified**: the native `UIPasteboard` round-trip specifically (`window.webkit.messageHandlers.nativePaste` → Swift → `evaluateJavaScript`) — this can only fire inside the real WKWebView, which isn't reachable from this session's tooling (no remote-debugging bridge to the simulator's WKWebView); the JS-side logic it calls into (`term.paste(text); term.focus();`) is proven correct via the desktop fallback path, and the Swift code mirrors the already-proven `nativeLog` `WKScriptMessageHandler` pattern in the same file, but the actual tap-to-paste round trip on device/simulator is the one remaining thing to confirm by hand.

## On-device (simulator) manual test found a real bug Playwright couldn't catch (2026-07-06)

Owner tested paste (worked, after re-approving the permission — expected, reinstalling resets pasteboard consent) and mouse-based select (didn't highlight) on the simulator. Also reported: click+drag pans the **entire page**, including the fixed "Leaning Technologies" nav header scrolling off-screen — not scrolling, not selecting.

**Root cause, confirmed by reading `ios/App/WasmWebView.swift`:** the `WKWebView` was fully stock — no `scrollView` configuration at all. WKWebView wraps its rendered content in its own native `UIScrollView`, which is a *separate mechanism* from CSS-level scrolling/overflow (already `overflow:hidden` on `body`) — its default pan/bounce behavior drags the whole rendered surface (nav header included, since a native scrollView offset repositions the entire content layer, not just document-flow-scrollable regions) whenever nothing else claims the gesture. This is a known WKWebView "app-like viewport" gotcha, not something introduced by this session's copy/paste patch.

**Why Playwright never caught it**: this is a native `UIScrollView` behavior specific to WKWebView on iOS — it doesn't exist in desktop Chromium at all, so no amount of Playwright touch-emulation testing could have surfaced it. This is a real, confirmed gap in this session's test coverage, not an oversight in how thoroughly Playwright was used.

**Fix**: `webView.scrollView.isScrollEnabled = false` and `bounces = false` in `WasmWebView.swift`'s `makeUIView` — disables the native page-level scroll/bounce entirely, leaving xterm.js's own internal `.xterm-viewport` (`overflow-y:scroll`, a normal nested DOM scroll region, handled independently by WebKit regardless of the outer WKWebView's scrollView setting) and the touch-selection bridge as the only things responding to touch/drag. Rebuilt and relaunched on the simulator; awaiting the owner's retest.

**On "no highlight" from a mouse select**: most likely explained by the interaction design, not a bug — `initTouchSelection`'s long-press gate requires ~450ms of no significant movement before arming selection (specifically so a quick drag still scrolls, rather than every drag accidentally starting a selection), and a normal mouse click-and-immediately-drag (natural instinct, unlike touch) wouldn't satisfy that. Asked the owner to retest with a deliberate pause-then-drag now that the pan bug (which may have been interfering) is fixed. If it still doesn't select with a proper long-press, that would point to a genuine discrepancy between the simulator's real mouse-to-touch event translation and the hand-constructed synthetic `TouchEvent`s used in this session's Playwright verification (which did work) — not yet ruled out, since no tap/drag automation tooling is available in this environment to test it directly (see the earlier Accessibility-permission and missing-`idb` notes).

## Selection still not working after the scrollView fix — reworked the gesture entirely (2026-07-06)

Owner reported the retest still didn't select, and asked to rethink the gesture rather than keep patching the long-press model: **double-tap (or double-click)-then-drag for instant word-based selection, dropping single-tap/click-drag from selection entirely** (reserved purely for scrolling). Bonus/deferred asks: selection-beyond-viewport-bounds, draggable selection handles, and reconfirming OSC 52 — explicitly "capture if not easy," with "for now: just double-tap and drag" as the actual scope.

**Good news found while implementing:** xterm.js already has real double-click word-selection built in (`SelectionService._handleDoubleClick`, triggered by `e.detail===2` on `mousedown`) — it selects the word under the cursor and switches to word-extend drag mode (`_activeSelectionMode=1`), which is exactly "double-click/tap and drag for word selection." No need to reimplement word-boundary logic; just needed to correctly trigger it from a detected double-tap.

**Rewrote `initTouchSelection`** (`src/lib/WebVM.svelte`): removed the long-press timer entirely. Now tracks the time/position of the last completed tap; a new touchstart within 300ms and 30px of it is recognized as the second tap of a double-tap and immediately dispatches a synthetic `mousedown` with `detail:2` (arms word-selection); the touch continuing to move (without lifting) dispatches `mousemove` (also `detail:2`) to extend the selection by whole words via xterm's own logic; a plain single-tap-drag is left completely untouched (no `preventDefault`, no synthetic events at all) so it falls through to whatever xterm's own scroll handling does — selection and scroll are now fully disjoint gestures instead of racing on a timer.

**Verification (Playwright, `term._core._selectionService` + a temporary `window.__testTerm` hook, reverted before rebuild):**
- First attempt showed `hasSelection()=true` but `getSelection()=""` — traced via the raw `SelectionModel` coordinates (`selectionStart`/`selectionStartLength`/`finalSelectionEnd`) down to a **test bug, not a code bug**: the test computed character width as `rowElement.rect.width / rowElement.textContent.length`, but the row's rendered width spans the terminal's actual column count (`term.cols`, 117 here), not the shorter visible-text length — this inflated the target x-coordinates, landing double-clicks near column 39 instead of the intended ~22 ("bravo"). Fixed the test to use `rect.width / term.cols`.
- With that fixed: double-tap on "bravo" then drag to "delta" (same row, `echo alpha bravo charlie delta`) produced `getSelection() === "bravo charlie delta"` — exactly the intended word-extend behavior. Copy correctly captured that exact text to the clipboard. A plain single-tap-drag (no preceding tap) correctly produced no selection and no Copy button.
- Found and fixed one small real bug along the way: the Copy button's click handler never called `term.clearSelection()`, so the highlight/selection state lingered after copying (visible as stale `hasSelection()=true` confusing a later regression check). Added the clear.
- **Selection-beyond-viewport (auto-scroll while dragging near an edge)**: tried to confirm this comes free via xterm's own internal `_dragScroll` (a 50ms-interval timer already wired up by `_addMouseDownListeners`, independent of anything built this session) — it did **not** engage in two attempts (dragging to both the top and bottom edge of `#console`). Likely needs continuous/repeated synthetic `touchmove` dispatches while held at the edge (mimicking a real finger holding position) rather than the one-shot dispatch used here — not chased further given it was explicitly "capture if not easy" and the owner's stated scope for this round was "just double-tap and drag." Left as an open, not-yet-working item, not silently assumed fixed.
- **Selection editing handles (draggable start/end markers)**: not attempted — xterm.js has no built-in touch-drag-handle UI at all (that's an iOS-native affordance this app would need to build from scratch: two draggable markers, hit-testing, syncing with xterm's selection model). Genuinely not easy; left as a deferred, larger future item per the owner's own framing.
- OSC 52: already implemented and verified in an earlier round of this session (real guest `printf` → real clipboard) — no new work needed, just confirmed still relevant/untouched by this rework.

Rebuilt (`WEBVM_MODE=ios`, disk re-staged) and relaunched on the simulator. Awaiting the owner's retest — the new gesture is **double-click (mouse) or double-tap (touch), then drag without releasing** for word-based selection; a single click/tap-drag now does nothing but whatever scrolling already happens by default.

## Word-select worked, drag-extend didn't — WKWebView's native double-tap-to-zoom was intercepting the gesture (2026-07-06)

Owner's retest: double-click/tap correctly creates a word selection, but dragging afterward doesn't extend it — a partial success that narrowed the problem precisely (the double-tap *detection* and initial `mousedown(detail:2)` dispatch both work correctly on real touch; only the follow-on drag fails).

**Root cause (by inspection, not yet device-confirmed):** `src/app.html`'s viewport meta tag had no `maximum-scale`/`user-scalable` restriction, so WKWebView's native double-tap-to-zoom `UIGestureRecognizer` is live. Once it *also* recognizes the same double-tap my JS does, it's a native UIKit-level recognizer — it plausibly claims/cancels the ongoing touch sequence for zoom purposes before the subsequent `touchmove` reaches my JS listener at all. This is consistent with word-select succeeding (evaluated synchronously on the qualifying `touchstart`, before any gesture-recognizer arbitration) while the drag silently fails (the native recognizer having taken over by then).

**Fix:** `<meta name="viewport" content="width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no" />` — disables pinch/double-tap zoom entirely, so there's no zoom range for that native recognizer to act on. Applied to the *shared* `app.html` (used by the public web build too, not iOS-only) — judged low-risk: `maximum-scale`/`user-scalable` only affect mobile touch pinch/double-tap zoom, desktop browser zoom (Cmd+/-) is unaffected, and the layout is already a fixed, app-like terminal UI (`overflow:hidden` on body, dynamically-sized terminal text) where pinch-zoom isn't a meaningful affordance to begin with — not a new restriction on an otherwise free-scrolling document.

**Verification:** re-ran the full Playwright double-tap+drag+copy regression after this change — `"bravo charlie delta"` still comes through correctly, confirming no regression on desktop/Chromium (expected, since these viewport attributes are a no-op there). **Could not verify the actual fix** (whether it stops the native gesture recognizer from intercepting on a real WKWebView) via Playwright — there is no desktop equivalent of WKWebView's native double-tap-to-zoom recognizer, so this specific behavior can only be confirmed on the simulator/device. Rebuilt and relaunched on the simulator; awaiting the owner's retest.

### `yank` worked in Playwright but not the simulator — added a native copy bridge (2026-07-06)

Owner reported `yank` didn't work in the sim. Root cause is the exact write-side mirror of the paste problem solved earlier: **`navigator.clipboard.writeText()` requires a user gesture / transient activation in WKWebView**, but the OSC 52 handler fires from **terminal output** (the guest writing the escape sequence), with no user activation — so WebKit silently rejects the write (and the handler's `.catch(()=>{})` swallowed it, hence no visible error). It worked in Playwright only because the test explicitly `grantPermissions(['clipboard-write'])`, which bypasses the gesture requirement — a real gap between the desktop test harness and the WKWebView target.

**Fix**: added a `nativeCopy` `WKScriptMessageHandler` (`ios/App/WasmWebView.swift`) that does `UIPasteboard.general.string = text`, and a `webvmCopy(text)` JS helper (`WebVM.svelte`) that posts to it when `window.webkit.messageHandlers.nativeCopy` exists, else falls back to `navigator.clipboard.writeText`.
